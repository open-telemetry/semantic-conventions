# Semantic conventions for span-derived metrics

**Status**: [Development][DocumentStatus]

This document defines the shape of metrics derived from spans ("span metrics"),
such as request rate, error rate, and duration.

A **span-metrics generator** is any component that observes ended spans and
records metrics from them, for example an SDK span processor, a Collector
connector, an eBPF agent, or a backend. Following these conventions lets
dashboards and alerts work the same way regardless of which generator produced
the data.

These conventions are additive. They define new names and do not change the
output of existing components.

## Recording span metrics

**Status**: [Development][DocumentStatus]

- The generator records one measurement per ended span it observes. Each span
  SHOULD be measured by only one generator in a telemetry pipeline.
- The metric's Resource MUST be the Resource of the span the measurement was
  derived from. Resource attributes, including `service.name`, SHOULD NOT be
  copied onto data points.
- The instrumentation scope SHOULD identify the generator, and its schema URL
  SHOULD be the semantic conventions version the generator implements.
- Generators MAY allow users to add attributes beyond the ones defined in this
  document, or to remove optional attributes. Generators SHOULD document such
  options.

### Cardinality

Span names are not guaranteed to be low cardinality, so
[`otel.span.name`](/docs/registry/attributes/otel.md) is Opt-In. Without it,
measurements are grouped by span kind, status, and `error.type`. Users who
know their span names follow span naming conventions can enable it.

Generators that apply a
[cardinality limit](https://opentelemetry.io/docs/specs/otel/metrics/sdk/#cardinality-limits)
SHOULD follow the metrics SDK overflow behavior.

### Single writer

Two generator instances that observe spans with the same Resource produce
the same metric streams, which violates the
[single-writer](https://opentelemetry.io/docs/specs/otel/metrics/data-model/#single-writer)
rule. Generators SHOULD avoid this by making sure that all spans with the same
Resource reach the same generator instance, for example by routing spans by
Resource, or by generating span metrics in the SDK or a node-local agent.
Generators SHOULD NOT add per-instance identifying attributes to data points to
work around this, because such attributes multiply the number of series and
change across deployments.

### Exemplars

Exemplars are optional. When recorded, each exemplar MUST reference the trace
ID and span ID of a span that contributed to the data point. Generators SHOULD
select exemplars as described by the metrics SDK
[`AlignedHistogramBucketExemplarReservoir`](https://opentelemetry.io/docs/specs/otel/metrics/sdk/#alignedhistogrambucketexemplarreservoir)
for explicit bucket histograms, and the
[`SimpleFixedSizeExemplarReservoir`](https://opentelemetry.io/docs/specs/otel/metrics/sdk/#simplefixedsizeexemplarreservoir)
for exponential histograms.

## Metric: `otel.span.duration`

**Status**: [Development][DocumentStatus]

This metric is [required][MetricRequired] for span-metrics generators.

This metric SHOULD be specified with
[`ExplicitBucketBoundaries` advisory parameter](https://opentelemetry.io/docs/specs/otel/metrics/api/#instrument-advisory-parameters)
of `[ 0.001, 0.0025, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10, 30, 60 ]`,
following the [duration histogram bucket boundaries](/docs/general/metrics.md#duration-histogram-bucket-boundaries)
guidance. Generators MAY use exponential histograms instead.

**[1]:** A span-metrics generator records exactly one measurement per ended span it observes.
The measured value is the span end timestamp minus the span start timestamp, in seconds.
If the end timestamp is earlier than the start timestamp, the generator MUST record `0`.

Throughput and error rate are derived from this histogram: the histogram count gives the
number of spans, and the count of measurements with `error.type` gives the number of failed
operations.

**[1] `otel.span.kind`:** Values are the SpanKind names defined by the Trace API, not the OTLP protobuf enum names
(for example `SERVER`, not `SPAN_KIND_SERVER`).

**[2] `error.type`:** if the operation described by the span ended with an error.

**[3] `error.type`:** When the span has an `error.type` attribute, the generator MUST use its value.
When the span status is `ERROR` and the span has no `error.type` attribute,
the generator SHOULD set `error.type` to `_OTHER`.
`error.type` MUST NOT be set when the operation succeeded.

**[4] `otel.span.name`:** The value MUST be the span name as reported by the instrumentation, unchanged.

Span names are not guaranteed to be low cardinality. Instrumentations that don't
follow span naming conventions can produce span names that contain identifiers,
for example `GET /orders/8812`.
