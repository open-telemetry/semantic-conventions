# General attributes

**Status**: [Development][DocumentStatus]

The attributes described in this section are not specific to a particular operation but rather generic.
They may be used in any Span they apply to.
Particular operations may refer to or require some of these attributes.

## Network attributes

Network communication is described by several families of attributes: `client.*` / `server.*`,
`source.*` / `destination.*`, and `network.local.*` / `network.peer.*`. Their definitions live in
the attribute registry:

- [`client.*`](/docs/registry/attributes/client.md) and [`server.*`](/docs/registry/attributes/server.md)
- [`source.*`](/docs/registry/attributes/source.md) and [`destination.*`](/docs/registry/attributes/destination.md)
- [`network.*`](/docs/registry/attributes/network.md)

For help choosing among these families, see
[Choosing network address and port attributes](/docs/network/choosing-network-attributes.md).

## General remote service attributes

<a id="service-peer"></a>

### Service identities

The resource's `service.name` and `service.namespace` identify the service producing the telemetry.
The `client.service.*` and `server.service.*` attributes identify the services participating in the
interaction, using the same logical roles as `client.address` and `server.address`.
An observer can record both the client and server service identities on the same signal.

For example, when `shoppingcart` calls `payments`:

| Observation point | Resource `service.name` | Span `client.service.name` | Span `server.service.name` |
| --- | --- | --- | --- |
| Client | `shoppingcart` | `shoppingcart`, if recorded | `payments` |
| Server | `payments` | `shoppingcart` | `payments`, if recorded |

The local service identity is already available on the resource, so recording it again on the span
is usually unnecessary.

| [`server.service.namespace`](/docs/registry/attributes/server.md) | ![Development](https://img.shields.io/badge/-development-blue) | `Opt-In` | string | Logical namespace of the service acting as the server in a connection-based network interaction. [4] | `Shop` |

**[1] `client.service.name`:** SHOULD be equal to the actual [`service.name`](/docs/resource/README.md#service) resource attribute of the logical client, if any. This identifies the client service whether the telemetry is recorded by the client, the server, or another observer.

**[2] `client.service.namespace`:** SHOULD be equal to the actual [`service.namespace`](/docs/resource/README.md#service) resource attribute of the logical client, if any. This identifies the client service's namespace whether the telemetry is recorded by the client, the server, or another observer. Together with `client.service.name`, this identifies the client service. An empty namespace is equivalent to an unspecified namespace.

**[3] `server.service.name`:** SHOULD be equal to the actual [`service.name`](/docs/resource/README.md#service) resource attribute of the logical server, if any. This identifies the server service whether the telemetry is recorded by the client, the server, or another observer.

**[4] `server.service.namespace`:** SHOULD be equal to the actual [`service.namespace`](/docs/resource/README.md#service) resource attribute of the logical server, if any. This identifies the server service's namespace whether the telemetry is recorded by the client, the server, or another observer. Together with `server.service.name`, this identifies the server service. An empty namespace is equivalent to an unspecified namespace.

## Source code attributes

**Status**: [Release Candidate][DocumentStatus]

Often a span is closely tied to a certain unit of code that is logically responsible for handling
the operation that the span describes (usually the method that starts the span).
For an HTTP server span, this would be the function that handles the incoming request, for example.
The [code attributes](https://opentelemetry.io/docs/specs/semconv/registry/attributes/code/) allow to report this unit of code
and therefore to provide more context.
