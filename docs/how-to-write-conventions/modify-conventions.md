# How to modify semantic conventions

This guide follows a change to existing conventions from an issue through review.
For the design of new conventions, see [How to write semantic conventions](README.md).
For repository setup and command details, see [Contributing](/CONTRIBUTING.md).

## Describe the change

Search existing issues and pull requests before opening a new issue. Describe
which telemetry is affected, the use case, and what the current conventions
cannot express. Include examples of the existing and proposed telemetry so
reviewers can assess the effect on instrumentations and consumers.

Check the area's status and owners in [Semantic Convention Areas](/AREAS.md).
Follow [Issue and PR triage management](/issue-management.md): before opening a
non-trivial pull request, the issue needs `triage:accepted:ready` or
`triage:accepted:ready-with-sig`. An issue marked
`triage:accepted:needs-sig` needs a group to form before implementation can
proceed. The triage document lists exceptions for trivial changes.

If triage requests more information, add the missing use cases, examples, or
prototype results to the issue. If the proposal is rejected, read the recorded
reason before preparing an implementation. Address that reason in the issue
rather than opening a pull request for the rejected proposal.

## Check compatibility

Identify the stability of each affected attribute, metric, or signal definition.
Compare the proposal with the [stability guarantees][stability] before editing.
A change to a development convention can still break generated libraries or
existing instrumentations.

Do not delete an attribute, metric, or enum member to replace it. Follow the
[model contribution guidance](/CONTRIBUTING.md#3-check-new-convention) for
deprecation and backward compatibility checks. Do not edit released files in
`schemas/`, which are generated by the release process.

For a change that requires users to migrate, describe how instrumentations and
consumers can move from the old convention to the new one. Include the
configuration and migration documentation needed to support that transition.

## Update the model and documentation

Set up the repository using the [contribution prerequisites](/CONTRIBUTING.md#prerequisites).
Modify the YAML definitions under `model/` and the explanatory text under
`docs/`. Reuse existing attributes where their meaning matches the use case.
Keep normative behavior in the documentation consistent with the model.

For non-trivial changes, prototype the proposal in the relevant instrumentation.
Link the implementation and results so reviewers can check that the data can be
collected and that the convention works for the intended use case. See
[Prototyping](README.md#prototyping) for what to validate.

Regenerate the documentation after changing the model:

```sh
make generate-all
```

Review the generated diff as well as the source changes. Update examples and
cross-references affected by the change. Add a [changelog entry](/CONTRIBUTING.md#5-changelog)
for user-facing changes, including changes to definitions or normative language.
Editorial changes and internal tooling changes do not need an entry.

## Validate and open the pull request

Run the repository checks before submitting:

```sh
make check
```

If a check fails, inspect its output, correct the source, regenerate affected
files, and rerun the check. The [automation reference](/CONTRIBUTING.md#automation)
describes how to run individual checks. Include the commands and results in the
pull request, with any checks that could not be run and the reason.

Link the accepted issue in the pull request and describe the behavior change.
Include links to prototypes or existing instrumentations and complete the pull
request template. Sign the [Contributor License Agreement](/CONTRIBUTING.md#sign-the-cla)
if it has not already been signed.

## Respond to review

Area owners review changes to their conventions, and a semantic conventions
approver reviews each pull request. Respond to questions with the relevant
use cases or prototype results. When a requested change affects the model,
regenerate the documentation and rerun the affected checks before requesting
another review.

Use the [merge requirements](/CONTRIBUTING.md#5-getting-your-pr-merged) to track
remaining approvals, discussions, and waiting time. Acceptance of an issue does
not guarantee acceptance of its proposed implementation. If the pull request is
closed, use the review explanation to determine whether to revise the proposal
in the issue or stop pursuing that change.
